# Engine Gap Tracker

A running log of every engine gap discovered while rebuilding strategies this
session -- what it was, when it was found, whether it's fixed, and which
strategy exposed it. Read-only historical record; append new entries at the
bottom as they're found, never rewrite/reorder past entries.

**Instruction for future work in this repo:** whenever a new engine
capability gap is discovered while building or fixing a strategy, add a row
to the table below (found date, strategy that exposed it, description,
status, fix location) before moving on -- don't let it live only in a chat
report.

| 13 | `_eval()`'s `_within()` (the "did this concept fire somewhere in the last N bars" window check) used a bare `.any()` on the cached numpy array -- correct for a plain boolean column, but a role-tagged condition's column is merged onto the entry index via `MultiTimeframeContext` (mtf_context.py), which is `NaN` (not `False`) for every entry bar before that role's FIRST higher-timeframe bar has even closed. Merging upcasts the column from bool to float/object, and `.any()` treats `NaN` as truthy (`NaN != 0`), not falsy -- spuriously firing a "concept happened" signal in the first few bars of a backtest purely because no data existed yet. Confirmed live: Laxman Rekha's `short_tf`-role short entries opened real trades at bar 0-2 of a BTCUSDT smoke test with `short_tf_laxman_trigger_high` still `NaN` (no 15m bar had closed yet) -- the resulting trades had no real stop-loss (silently fell through to the emergency %-fallback, since THAT lookup correctly uses `_get()`'s `pd.isna()` check) and no take-profit at all. | Laxman Rekha 5-EMA Trigger-Candle Strategy build (its unusual two-different-entry-timeframes-per-direction design exposed this) | Fixed | `configured_strategy.py` `_eval()`'s `_within()`: `arr.any()` -> `(arr == True).any()`, which correctly excludes `NaN` (`NaN == True` is `False` for both float and object dtypes) while leaving every genuine `True` value unaffected. Full regression suite re-run after this fix. Correction: an earlier draft of this row claimed no existing strategy was affected -- checked directly and that was wrong. At least 9 of the 14 existing strategies use a role-tagged concept condition on a non-entry `bias`/`structure` role (`valid_structure_trend`, `sweep_invalidation_state`, `choch`, `bos`, `pdh`/`pdl`, `support`/`resistance`), so this fix is a genuine correctness improvement for their FUTURE re-runs too (their leading NaN window could no longer spuriously fire). Their already-saved batch results reflect the OLD (buggy) behavior; re-running all 14 to quantify the exact before/after difference was outside this task's scope (it only asked to build 2 new strategies) and was not done here -- flagged as a real follow-up worth doing, not silently skipped. |
